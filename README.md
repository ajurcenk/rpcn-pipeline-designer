# Pipeline Designer for Redpanda Connect

A VS Code extension for [Redpanda Connect](https://docs.redpanda.com/redpanda-connect/) configs: a read-only pipeline graph beside the YAML editor, Redpanda Connect-aware YAML editing, and local runs.

> **Status: early proof of concept (0.0.1).** This build finds the Redpanda Connect binary and builds the config schema from it, and adds schema-backed completion and hover, lint on save with Quick Fixes, Bloblang highlighting and completion, pipeline snippets, and Run and Stop, and a first read-only pipeline graph. Details go to the **Redpanda Connect** output channel.

## Installing

The extension is not on the VS Code Marketplace or Open VSX yet; install it from a `.vsix` file.

1. Get the `.vsix`, either way:
   - **From CI:** every green build on `main` uploads it as the `rpcn-pipeline-designer-vsix` artifact. Download it from the run's page under **Actions** (it comes zipped), or with the GitHub CLI:

     ```sh
     gh run download --repo ajurcenk/rpcn-pipeline-designer -n rpcn-pipeline-designer-vsix
     ```
   - **Built locally:** `npm ci`, then `npx vsce package --no-dependencies`.
2. Install it: `code --install-extension rpcn-pipeline-designer-0.0.1.vsix`, or in VS Code open the Extensions view, then **…** → **Install from VSIX…** and pick the file.

VS Code installs [YAML by Red Hat](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml), which the extension depends on, from the Marketplace (internet access is needed the first time). The extension also needs your Redpanda Connect binary; see [Requirements](#requirements) and [Finding the binary](#finding-the-binary). The version stays 0.0.1 for now, so to update, install the newer `.vsix` with `code --install-extension <file> --force` (or uninstall first) and reload the window.

## Finding the binary

When the extension activates (the first time a YAML file opens), it looks for Redpanda Connect in this order:

1. `rpk` on `PATH`, run as `rpk connect` (needs `rpk connect install`).
2. `redpanda-connect` on `PATH`.
3. `redpandaConnect.binaryPath`, used only when `PATH` gives no usable binary. A value naming `rpk` runs as `rpk connect`.

A binary older than v4.100.0, or one whose version check fails, is not used. The binary is looked up again when `redpandaConnect.binaryPath` changes and on **Redpanda Connect: Refresh Schema**.

If no usable binary is found, a warning appears once (and again only after the state changes) with three actions:

- **Install guide** opens the [Redpanda Connect install docs](https://docs.redpanda.com/connect/install/).
- **Set path** picks a binary and saves it to the user setting `redpandaConnect.binaryPath`.
- **Retry** looks for the binary again.

## Schema

For the resolved binary, the extension runs `list --format jsonschema` and merges in the field descriptions, examples and defaults from `list --format json-full`. The result is cached in the extension's global storage as `schema-<hash>.json`, whose name changes with the binary path, its version and the transform version. Later activations still run `--version` to find the binary, but on a cache hit they skip both `list` runs. After a successful write (never on a cache hit), other `schema-<16 hex>.json` files unused for more than 30 days are removed.

**Redpanda Connect: Refresh Schema** looks for the binary again and regenerates the schema, even when a cached copy exists; with no usable binary it says so in the output channel and shows the binary warning again. Open files pick up a new binary or schema (Set path, Retry, Refresh Schema) without being reopened. The schema is served to YAML by Red Hat for detected configs only (completion and hover). The served schema drops `required` (lint on save reports missing fields), so a component's fields are still offered while a required one is missing, and fields with documented options (for example `codec` or `logger.level`) suggest those values with their descriptions and list them in their hover (`Options: …`); any other string stays valid. YAML by Red Hat offers nothing in an empty block below the top level (`socket:` with nothing under it yet) or on an empty value inside a component (`network: `); there the extension adds the fields (also while the first key is partly typed) or the options (true/false for switches) itself, from the same schema, and stays silent everywhere else so nothing appears twice. In a new, empty component block the list starts with **<component>: required fields**, which inserts the fields the component needs in one go (for `socket`: `network`, a choice of `unix`/`tcp`, and `address`). An empty list item inside a component gets the same help: processor or output names in a nested `processors:` / `outputs:` list (for example in a `switch` case), and the item's fields in a list of objects (for example `switch` cases or `tls.client_certs`).

## Which files are Redpanda Connect configs

An open YAML file is treated as a Redpanda Connect config when one of its YAML documents has a top-level `input`, `pipeline`, `output`, `buffer` or `*_resources` key (`cache_resources`, `rate_limit_resources`, `processor_resources`, `input_resources`, `output_resources`). Templates (a document with top-level `name`, `type` and `mapping`) are not. A file matching a `redpandaConnect.filePatterns` glob is always treated as a config, templates included. Detection follows edits and setting changes; there is no need to reopen the file. Resource files are not found automatically: lint and run pass exactly the files in `redpandaConnect.resourceFiles`.

## Snippets

In a Redpanda Connect file, completion also offers starters marked *snippet*. At the top level: a whole pipeline (also in a completely blank YAML file), or an `input`, `pipeline` or `output` section the file does not have yet. Under `input:`: `generate`, `redpanda`. Under `output:`: `redpanda`, `stdout`. On any `processors:` list item, including nested ones in `switch` or `branch`: `mapping`, `switch`, `branch`, `log`. Each inserts a block that lints clean as is; Tab moves through its placeholders. Type the component name (or `rpcn-` for the sections) to find them.

## Bloblang

Bloblang is highlighted in the values of Redpanda Connect mapping fields (`mapping`, `mutation`, `bloblang`, `check`, `request_map`, `result_map`, `args_mapping` and the other `*_mapping` / `*_map` fields), as a block (`|`), a plain or a quoted value, and in `${! … }` interpolations inside any YAML string. Inside Bloblang, completion offers the Bloblang **functions** (`now()`, `uuid_v4()`, …) and, after a dot, the **methods** (`.uppercase()`, `.parse_json()`, …) of your binary's version, with descriptions and parameter placeholders, and hovering a function or method name shows its docs and an example. They come from the binary's own docs (`list --format json-full`), so they match the version you run. After `this.` or `root.` (and deeper, such as `this.user.`), the fields your config already writes or reads above the cursor come first: the same mapping, then earlier steps (an input's `generate` mapping, earlier processors), including the keys of object literals such as `root.user = {"name": …}`; each says where it came from ("assigned on line 23"). `$` offers your `let` variables and `@` your metadata keys. When the type before the dot is known, the methods are narrowed to it: after a literal (`"test".` offers string methods, `[1, 2].` array methods, `{…}.` object methods) or a field assigned one above (`root.n = 5`, then `this.n.` offers number methods). Otherwise all methods are offered. This is read from the config, not from the messages, so fields that only arrive in the input data appear once you have used them. While you type in a `mapping` or `mutation` processor of a detected config file (not an untitled one), its Bloblang is checked by your binary (`blobl`, about 300 ms after you stop typing, only for the processors you changed): a syntax error is underlined at the binary's line and column with its message (source `Bloblang`), and clears once the mapping parses. Nothing is checked while the YAML itself does not parse, without a usable binary, or in untitled files; an unset `${VAR}` is not a syntax error, so it only writes a line to the output channel (set `redpandaConnect.envFile` to give it a value). Other Bloblang fields and `${! }` interpolations are not checked while typing; lint on save checks them, and on save lint's own report of an error that is already underlined is hidden. Generic field names that also hold Bloblang in a few components (`when`, `query`, …) are not highlighted, because the highlighting applies to every YAML file.

## Bloblang test panel (preview)

In a detected config, every `mapping` and `mutation` processor (in any `processors` list, nested ones and `processor_resources` included) gets a **▷ Test mapping** CodeLens on its key line; **Redpanda Connect: Test mapping** in the Command Palette does the same for the processor at the cursor (elsewhere it says "Put the cursor in a mapping or mutation processor, or a generate input's mapping."). It opens a panel named "Bloblang: <label>" (or the processor's path, such as `pipeline.processors[0]`) beside the editor, one per processor, without taking focus from the YAML; running it again brings that panel to the front. The panel has an **Input** and an **Output** column, each with **Content** and **Metadata** tabs. Type the message content (usually JSON) into the input's Content tab, and add metadata in its Metadata tab (a Key / Value table: **+ Add metadata**, **Remove**; rows with an empty key are not sent, and when a key repeats the last row wins). With **Run on change** (on by default) the processor's current Bloblang runs once on the input with your binary 300 ms after you stop editing the content, the metadata or the mapping itself; with it off, only **Run** runs it. The output's Content tab shows the output, pretty-printed when it is JSON, with the lines of every added or changed top-level field marked; its Metadata tab lists the output metadata (`meta` keys the mapping set or kept), with added and changed keys marked. The footer lists the changes as tags, `+field` added, `~field` changed, `−field` removed, metadata keys as `@key`, or says "No changes". The status pill in the header reads "✓ Ran in <N> ms · <binary>". Every other result has its own card and status pill. A mapping that does not parse shows "✕ Syntax error · not run" and "Mapping doesn't parse" with the binary's message and caret excerpt, at the mapping's line and char and the file's line (`mapping line 2, char 10 · orders.yaml line 14`, the same place the editor underlines). A mapping that fails on the input shows "✕ Mapping failed on this input" and "Failed on mapping line N" with the file line and the binary's message, and the failing line ends with ` ✕ fails on this input` in the editor until the next result (or until that line leaves the processor, or the panel closes). Both offer **Go to line**, which puts the cursor at the start of that line in the YAML editor. An input the mapping can't read as JSON (`this` on text that is not JSON) shows "This input can't be read by the mapping" with a hint to check the input's Content; a message the mapping deleted shows "⊘ Message deleted" and "No output and no metadata."; and a run that could not happen at all (an unset `${VAR}`, no binary, a timeout) shows "The test could not run" with the binary's own message. Under an error, the last successful output since the panel opened stays, dimmed and unmarked, labelled "Last successful output". The input, its metadata, the selected tabs and Run on change are kept when the panel is reloaded, and a reloaded panel runs its input once (with Run on change on). A test is a one-message `run` of a temporary config in the extension's storage, deleted afterwards, with the `redpandaConnect.resourceFiles` and `redpandaConnect.envFile` settings and a 10 s limit; a `mutation` keeps the input's fields, as in a pipeline. The metadata is set on the message by the temporary config's `generate` input, so the mapping reads it with `@key` / `metadata("key")`. Untitled files are not tested: save the file first. Sample files are not there yet.

A `generate` input's `mapping` (`input.generate`, or a `broker`'s `inputs` entry) gets the **▷ Test mapping** lens too, and Test mapping at the cursor in it opens its panel, named "Bloblang: <label>" (or its path, such as `input.generate`). That panel is output only: no Input column and no samples. It runs once when it opens and shows the one message the mapping generates, content and metadata, without change marks or a "Changed:" footer; **Run** gives a fresh one, and with Run on change on it re-runs when you edit the mapping (`count` and `interval` are ignored). The mapping runs as a `mapping` processor on one empty message, the message a real `generate` input's mapping starts from, so it gives the same output and errors as the input would, shown with the cards above (a mapping that reads `this` shows the binary's "message is empty" error). One difference: `root = deleted()` shows "⊘ Message deleted", while a real `generate` input produces nothing and never ends.

## Lint on save

Saving a detected config runs `lint --deprecated --skip-env-var-check` with the `redpandaConnect.resourceFiles` and `redpandaConnect.envFile` settings, and shows each finding as a diagnostic on its whole line (source "Redpanda Connect"): `field … is deprecated` as a Warning, everything else as an Error. A finding on a line YAML by Red Hat already flags is hidden, and lint's YAML syntax errors are hidden while YAML by Red Hat reports a syntax error (it places them more precisely). File paths containing `*`, `?` or `[` are linted as written, not as patterns. The first edit after a save clears the findings until the next save. For `field X not recognised`, the light bulb offers **Change to `<name>`** for up to three of the closest field names that are valid at that spot in the schema; applying one replaces only the key. For `value X is not a valid option for this field` (a closed option list, enforced by lint), it offers the closest options of that field (or all of them when the list has at most five and none is close); applying one replaces only the value, quoting it when YAML would otherwise read it as something else (`"OFF"`, `"no"`). Because the first edit clears every finding, fixing them one by one would need a save after each fix; so when two or more findings in the file have a clear best fix, the light bulb on any of them also offers **Fix all lint findings with a clear fix (N)**, which applies all of those fixes as one edit (one undo step). Findings without a clear best fix (a tie, or a list of all options) are left for you. Lint does not run while you type, and problems running it (for example a relative `resourceFiles` entry with no workspace folder open) are written to the "Redpanda Connect" output channel.

## Run and Stop

**Run** (the play button in the editor title of a detected config, or **Redpanda Connect: Run**) saves unsaved changes and runs the file with `run --set http.enabled=false`, plus the `redpandaConnect.resourceFiles` and `redpandaConnect.envFile` settings. The output goes to a terminal named "Redpanda Connect: <file>", one per file, which is reused when you run the file again. The process is started directly, not through a shell. Its working directory is the file's workspace folder, or the file's directory when it is in none.

**Stop** (the status-bar item, Ctrl+C in that terminal, or **Redpanda Connect: Stop**) sends an interrupt and, if the pipeline is still running after 10 s, kills it; pressing Stop again kills at once. When the run ends, the status bar shows how it ended ("Pipeline stopped" for a run you stopped, otherwise "Pipeline exited (code N)"), and the terminal keeps the output. Closing the terminal ends its run; a Stop or close while a re-run is waiting for the old run to end cancels the restart. Untitled files cannot be run: save the file first. Known limit: in a multi-root workspace, relative `resourceFiles` / `envFile` settings resolve against the first folder, while the run's working directory is the file's own folder.

## Pipeline graph

The first time an editor shows a detected config in a window session, its graph opens in a panel named "Graph: <file>" beside the editor, one per file, and the cursor stays in the YAML. Graphs share one editor group, which is locked so that files you open land beside the YAML, not among the graphs. Turn this off with `redpandaConnect.autoOpenGraph`. A config that only becomes a Redpanda Connect config while you type, and an untitled file, get no automatic graph. In the editor title of a detected config, **Show graph** (also in the Command Palette as **Redpanda Connect: Show graph**) opens the graph, or brings it to the front, and **Hide graph** closes it. Hide graph is remembered per file in the workspace, also after a reload: that file's graph no longer opens by itself until you run Show graph on it. Show graph also marks the file as a Redpanda Connect config for the rest of the session, so it stays detected while you edit it. Closing the file's last editor tab closes its graph, and renaming the file keeps its graph (and its Hide) with the new name; **Save As** is not followed: the old graph closes with its tab and the new file gets its own. The graph draws every component of the config: the input, the `pipeline.processors` in order and the output, left to right and joined by arrows, plus the components nested inside others (`switch` cases, `branch`, `try` / `catch`, `workflow` branches, broker and fallback outputs, batching processors, …) and the `*_resources`. Which fields hold nested components comes from your binary's schema, so plugins and components of newer versions are found too. Without a usable binary the panel draws no pipeline and says "No Redpanda Connect binary. The graph needs it to read the schema.", with **Install guide**, **Set path** and **Retry** buttons that do what the binary warning's actions do; once a binary is found (or set), the graph draws in the same panel, without reopening it. While the schema loads the canvas stays empty. A config with nothing to draw yet (no `input`, `pipeline`, `output` or resources) says "Nothing to draw yet. Add an `input`, `pipeline` or `output` section." and the first component you type appears in its place. Groups (`switch`, `branch`, `try` / `catch`, `workflow`, brokers, …) are drawn as boxes holding their children, with a header showing the component and its label; `switch` cases, broker output lists, `try` / `catch` bodies and `workflow` branches are captioned boxes inside their group, and resources stand alone beside the flow. Every group starts expanded: its chevron collapses it to a single box with a count of what it hides ("3 cases", "4 processors"), and a collapsed group stays collapsed when the graph is drawn again. The graph uses the VS Code theme's colours and Codicons, and you can pan and zoom it; nothing can be dragged. Navigation works both ways. Clicking a node selects that component's YAML and centres it in the editor you were last working in (with the file split into two editors, the one whose cursor you last moved); clicking a group's header label selects the whole group. Moving the cursor through the YAML highlights the node under it in the graph (the innermost one, or the collapsed group box that hides it); the highlight never takes focus from the editor or brings the panel to the front, and while the YAML does not parse it stays where it was. The graph is read-only and follows your edits as you type, keeping your pan, zoom and collapsed groups (also when the panel is hidden and shown again); whitespace, comments and values not shown in the graph move nothing. While the YAML does not parse, the graph keeps the last valid version under a banner, "YAML has errors — showing last valid graph.", followed by the parser's message; clicking the banner selects the error in the editor, and the banner goes away as soon as the YAML parses again. A file that does not parse when the graph opens shows the banner over an empty canvas. Nodes with problems are marked: a node that lint (on save) or YAML by Red Hat reports an error on gets a thicker error-coloured border and an error icon in its corner, and one with only warnings (deprecated fields) a warning border and icon; an error wins over a warning. Hovering a marked node lists its messages from the Problems panel, verbatim (up to 20, then a count of the rest); an expanded group or `switch` case lists only the messages on its own lines. An expanded group or `switch` case is marked only for problems on its own lines (its children carry their own markers), while a collapsed group shows the worst problem of everything it hides. The markers follow the diagnostics: lint's clear with them on the first edit after a save, and while the YAML does not parse the graph keeps the markers it last showed. The markers only show what the editor reports; the graph offers no fixes. Closing the panel itself (its ×) is not a Hide: the file's graph is not suppressed. A closed graph no longer follows the file.

The graph works from the keyboard. Tab enters it at the first node (the input), or at the node you last focused, and Tab again leaves it: the graph is a single Tab stop. The arrow keys move between nodes: Right and Left to the next and previous node at the same level, Down into an expanded group or `switch` case (its first child), Up out to the enclosing one; a collapsed group is one stop. The focused node has the theme's focus ring. Enter selects the node's YAML and moves focus to the editor, as a click does; Space collapses or expands a group; Esc moves focus from a node to the graph itself, and Esc again returns focus to the YAML editor, leaving its cursor where it was. Screen readers hear the graph as "Pipeline graph, read-only" and each node by its role, component, label and problem ("Processor mapping, has error: field topic is required"; a group also says what it holds and whether it is expanded or collapsed), and a polite announcement reports the invalid-YAML banner and each node that gets a new error. Moving the cursor in the YAML never moves keyboard focus in the graph, and the graph has no keybindings of its own in VS Code.

## Requirements

- VS Code 1.100 or newer.
- [YAML by Red Hat](https://marketplace.visualstudio.com/items?itemName=redhat.vscode-yaml) (`redhat.vscode-yaml`). VS Code installs it automatically with this extension.
- Redpanda Connect v4.100.0 or newer: `rpk` on `PATH` with `rpk connect install` run, or a `redpanda-connect` binary on `PATH`; otherwise its location in `redpandaConnect.binaryPath`.

## Settings

| Setting | Default | Description |
| --- | --- | --- |
| `redpandaConnect.binaryPath` | `""` | Fallback path to the `redpanda-connect` or `rpk` binary. `PATH` is tried first (`rpk connect`, then `redpanda-connect`); this setting is used only when neither is usable. `~` expands to the home directory, a relative path resolves against the first workspace folder, and a bare name is looked up on `PATH`. |
| `redpandaConnect.autoOpenGraph` | `true` | Open the graph beside a detected config the first time an editor shows it in a session (not for a file you hid with **Hide graph**). |
| `redpandaConnect.filePatterns` | `[]` | Globs always treated as Redpanda Connect configs, matched relative to the file's workspace folder or against its absolute path: `*.rpcn.yaml` matches only at a folder root, `**/*.rpcn.yaml` anywhere. |
| `redpandaConnect.resourceFiles` | `[]` | Resource files passed to lint and run (`--resources`), each entry may be a glob. `~` expands to the home directory; a relative path resolves against the first workspace folder. |
| `redpandaConnect.envFile` | `""` | Environment file passed to lint and run (`--env-file`). `~` expands to the home directory; a relative path resolves against the first workspace folder. |

## Development

```sh
npm ci
npm run compile          # type-check, lint, bundle to dist/
npm test                 # unit + integration tests, twice: latest stable VS Code and VS Code 1.100.0 (the engines floor)
npx vscode-test --label floor     # one of the two (stable | floor), after npm run pretest
scripts/spike/fetch-binaries.sh   # pinned Redpanda Connect 4.100.0 and 4.112.0 into .cache/ (needs an authenticated gh)
npm run test:corpus      # lint every test/corpus/*.yaml with both binaries and compare with the recorded output;
                         # also checks the extension's diagnostics match every record (diagnostics parity) and
                         # that the graph model of every config matches test/corpus/<name>.graph/<ver>.json
                         # (graph accuracy); parity and graph accuracy need no binary
npm run test:corpus:record   # rewrite the lint and graph records (and delete orphaned ones)
npx vsce package --no-dependencies
```

Press F5 in VS Code to start an Extension Development Host, or run `scripts/dev-host.sh [folder] [file...]` to rebuild and (re)start a VS Code window with the extension loaded from source; its profile, YAML by Red Hat and default workspace live in the git-ignored `.dev-host/`.
