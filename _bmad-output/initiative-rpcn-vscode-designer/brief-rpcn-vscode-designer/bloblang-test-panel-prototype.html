Design notes

1
Entry point in the editor.

A CodeLens above each mapping: and mutation: opens the panel for that processor and shows how many samples it has. The graph node gets the same action. Syntax errors are underlined as you type, with the binary's message on hover.

2
One panel per mapping.

The header names the processor by its label and its position, and follows the mapping while you edit. The status pill always says what the last run did and which binary ran it.

3
Samples live in the workspace.

Each mapping has a list of named samples (content and metadata) in one JSON file under .rpcn/samples/, so they can be committed with the pipeline. Switching samples re-runs the mapping.

4
Input: content and metadata.

The content is any text (JSON for most mappings); metadata is a key/value table. Both are editable, and with Run on change the output follows each edit.

5
Output shows what changed.

Added or changed fields and metadata keys are marked, and the footer lists them. When the mapping fails, the last output stays dimmed under the error so the change is easy to compare.

6
Errors point at the YAML.

A mapping line is translated to the file line (mapping line 2 is orders.yaml line 12), and Go to line selects it in the editor. A failure that only happens on one sample is also shown at the end of that line.

Open questions this prototype doesn't settle

  • Metadata on today's binaries: blobl server ignores input metadata and returns none, so the panel would run each test as a one-message pipeline through run. A spike measures how long a run takes.
  • Linking samples to mappings: by the processor's label (shown here), with an offer to add a label when a mapping has none.
  • Mapping that reads earlier steps: the sample is the message as it reaches this processor; running the earlier processors first is out of the second release.
